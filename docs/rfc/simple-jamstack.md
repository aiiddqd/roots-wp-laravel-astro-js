## Вводные

Развиваем текущий Astro-проект в демонстрационный сайт-визитку парикмахера-стилиста. Публичная часть остаётся статическим сайтом (SSG); рядом появляется маршрут `/my` с формой входа и минимальным личным кабинетом. Учётные записи и проверка пароля остаются в существующем WordPress (Bedrock + Acorn); Astro не хранит пользователей и не получает секретов на этапе сборки.

Для v1 выбираем бесплатный плагин [JWT Authentication for WP REST API](https://wordpress.org/plugins/jwt-authentication-for-wp-rest-api/): он выдаёт токен на `POST /wp-json/jwt-auth/v1/token` и проверяет его через `POST /wp-json/jwt-auth/v1/token/validate`. Пакет `wp-plugin/jwt-authentication-for-wp-rest-api` уже закреплён в `wp/composer.lock` на 1.5.0, а `JWT_AUTH_SECRET_KEY` уже определён в `wp/config/application.php`; это не новая зависимость, а настройка и ввод в эксплуатацию имеющейся.

## Назначение и цели

- Получить первую версию сайта стилиста: главная страница с услугами, работами/призывом записаться и ссылкой «Личный кабинет».
- Сохранить преимущество Astro: публичный HTML генерируется при `astro build`, Node-сервера в production для него нет.
- Разрешать доступ в `/my` только после успешной аутентификации в WordPress; пароль передаётся только в HTTPS-запросе к WordPress API.
- Завести воспроизводимую локальную проверку и UI E2E-тесты Playwright: успешный вход, неверный пароль, восстановление сессии в пределах вкладки и выход.

Заинтересованные стороны: владелец сайта (принимает текст и визуальную часть), пользователь личного кабинета и разработчик, поддерживающий WordPress/Astro. Ревью RFC выполняет инициатор эксперимента.

## Составляющие и особенности

### Границы решения

| Часть | Решение v1 |
| --- | --- |
| Публичный сайт | Astro + TypeScript + Tailwind/DaisyUI, SSG; `/` — мини-визитка стилиста. |
| Личный кабинет | Статически собранный `/my` с клиентским TypeScript-скриптом; до входа видна только форма. |
| Identity provider | Существующий WordPress; создание пользователей и роли — в WP-админке/WP-CLI. |
| Сессия | JWT держится только в `sessionStorage`: переживает обновление страницы, удаляется при закрытии вкладки и при явном выходе. |
| Данные кабинета | В v1 отображаются безопасные поля ответа JWT-плагина: `user_display_name`, `user_email`, `user_nicename`. Записей, бронирований, изменения профиля и новых WP REST endpoints пока нет. |

`/my` не требует Astro SSR: при сборке создаётся нейтральный HTML, а браузер после отправки формы вызывает WordPress. Это означает, что URL `/my` сам по себе не скрывает статический файл; защита будущих пользовательских данных всегда должна выполняться WordPress REST API по заголовку `Authorization: Bearer <JWT>`, а не только состоянием интерфейса.

### Контракт авторизации

1. Форма отправляет `username` и `password` JSON-запросом на `${PUBLIC_WP_API_URL}/wp-json/jwt-auth/v1/token`.
2. При ответе 200 клиент кладёт только `token` в `sessionStorage`; отображаемое имя и email берёт из того же ответа. Пароль не логируется и нигде не сохраняется.
3. При открытии или перезагрузке `/my` клиент читает токен и вызывает `POST …/token/validate` с Bearer-заголовком. Успех показывает кабинет; ошибка/просрочка очищает storage и возвращает форму.
4. «Выйти» удаляет token и пользовательские данные из `sessionStorage`, затем показывает форму.

`PUBLIC_WP_API_URL` — публичная конфигурация клиента (локально `http://wp-roots.localhost`), не секрет. Адрес не хардкодится в `src/lib/wp.ts`: и сборочный fetch публичного контента, и клиент авторизации используют одну переменную с подходящим значением по умолчанию для local. Не использовать `PUBLIC_` для JWT-ключа, учётных данных или любого серверного секрета.

### WordPress и безопасность

- Активировать плагин из `wp/` через `./vendor/bin/wp … --allow-root` в lerd, не ручной копией в `web/app/plugins`.
- Добавить `JWT_AUTH_SECRET_KEY` в `wp/.env.example` только как непроизводственный placeholder; настоящее длинное случайное значение находится в неотслеживаемом `wp/.env`/секрет-хранилище. Ключ не равен WordPress salts и не попадает в фронтенд или логи.
- В небольшом mu-plugin задать срок JWT в один час фильтром `jwt_auth_expire`. Бесплатная версия плагина не предоставляет refresh и отзыв токенов, поэтому после истечения пользователь входит заново; мгновенный server-side logout не заявляется.
- Явно проверить передачу `Authorization` от production Nginx до PHP-FPM. Для разных origin настроить CORS/preflight ровно для локального Astro-origin и будущего публичного origin; не оставлять правило «любой origin» как окончательную production-настройку. В production обязательны HTTPS для обоих origin.
- Создать отдельного E2E-пользователя с ролью `subscriber`; существующие администраторские данные не использовать в тестах. Пароль E2E хранится локально в игнорируемом `.env.e2e`, читается Playwright через environment variables и не выводится в отчётах.

### Тесты и запуск

В `astro/` добавить `@playwright/test`, `playwright.config.ts`, команду `npm run test:e2e` и Chromium через `npx playwright install --with-deps chromium` (или эквивалент для среды). Конфигурация Playwright поднимает `npm run preview -- --host 127.0.0.1 --port 4321` через `webServer`; WordPress должен быть предварительно запущен и доступен по `PUBLIC_WP_API_URL`.

E2E-спека покрывает браузерный путь, а не подменяет WordPress API моками:

- гость на `/my` видит доступную форму входа, а пароль не присутствует в URL;
- действительные credentials приводят к видимому имени тестового пользователя и к успешной валидации JWT;
- неверный пароль показывает нейтральную ошибку, не создаёт сессию и не раскрывает, существует ли пользователь;
- reload в той же вкладке сохраняет доступ после повторной валидации; «Выйти» очищает сессию и снова показывает форму;
- `astro check`, `astro build` и E2E проходят, а поиск по `dist/` подтверждает отсутствие `JWT_AUTH_SECRET_KEY`, паролей и JWT тестовой сессии.

## Критерии приемки

- [ ] Главная `/` — SSG-страница-визитка стилиста, использующая DaisyUI; `astro build` не зависит от личного кабинета и завершается успешно.
- [ ] Статический маршрут `/my` содержит доступную форму входа и не содержит персональных данных либо токена до входа.
- [ ] JWT-плагин активирован, `JWT_AUTH_SECRET_KEY` задан только в локальной/production-конфигурации, а `wp/.env.example` описывает требуемую переменную без значения секрета.
- [ ] POST с E2E-пользователем к `/wp-json/jwt-auth/v1/token` выдаёт JWT, а `token/validate` с Bearer-заголовком возвращает 200; неверные данные возвращают ошибку без токена.
- [ ] CORS/preflight и передача `Authorization` проверены для origin Astro; производство использует HTTPS и конкретный allowlist origin.
- [ ] Токен не хранится в `localStorage`, cookie или собранных файлах; logout и неуспешная валидация очищают `sessionStorage`.
- [ ] `npm run test:e2e`, `npm run build` и `npx astro check` успешно проходят в чистом локальном запуске; E2E использует отдельного subscriber-пользователя и секреты вне Git.
- [ ] Backend зарегистрирован в lerd и доступен до E2E, Astro preview доступен на локальном порту; документация содержит точный порядок команд.

## Дорожная карта

1. Проверить/создать lerd-профиль Bedrock, связать `wp/` как `wp-roots`, поднять MySQL и выполнить `env setup` + `framework setup`; убедиться, что `/wp-json/` доступен.
2. Активировать уже установленный JWT-плагин, задать секрет и часовой TTL, создать E2E subscriber. Выполнить запросы token/validate вручную без вывода токена в журнал.
3. Вынести URL API в frontend-конфигурацию, сверстать публичную визитку и статическую страницу `/my` с клиентской логикой сессии.
4. Настроить CORS и Nginx forwarding, затем проверить auth flow из реального Astro preview.
5. Установить Playwright, реализовать E2E-спеки и добавить в README команды локального запуска, сборки и тестирования.
6. Выполнить весь acceptance checklist. Только после этого решить, нужны ли отдельные WP REST endpoints для записей к стилисту.

## Альтернативные варианты

### Astro SSR с HttpOnly-cookie

Даёт более традиционную сессию и не выдаёт JWT JavaScript-коду, но требует Node/edge runtime, adapter и серверного прокси. Это ломает цель простого SSG-эксперимента, поэтому откладывается до появления действительно чувствительных данных или длительных сессий.

### Хранить JWT в localStorage

Переживает закрытие браузера, но увеличивает последствия XSS и усложняет отзыв токена. Для v1 отклонён в пользу `sessionStorage` и короткого TTL.

## Итого и рекомендации

Рекомендуется реализовать `/my` как лёгкий клиентский слой поверх неизменного Astro SSG и уже добавленного WordPress JWT-плагина. Это минимально проверяет архитектуру «статичная визитка + авторизация в CMS», честно ограничивает v1 кабинетом-профилем и оставляет SSR/настоящие персональные данные следующей итерации.

## Открытые вопросы

- Какой публичный production-домен станет разрешённым CORS-origin для Astro и будет ли Astro развёрнут на отдельном поддомене?
- Что должен содержать кабинет после профиля: заявки на запись, календарь мастера или редактирование данных? Для любого из вариантов нужен отдельный защищённый WP REST contract и отдельный RFC.
